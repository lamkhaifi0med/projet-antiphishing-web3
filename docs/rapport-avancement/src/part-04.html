Mortalité des menaces

Neuf des dix échecs dead phishing sont des ENOTFOUND : les domaines ne résolvaient déjà plus au moment de la capture. Capturer tôt est donc déterminant.

Longueur du contenu

La médiane du texte phishing capturé est de 285 caractères contre 3 756 pour le légitime, soit environ treize fois moins. Ce signal peut devenir un biais si le modèle apprend « court = phishing ».

Biais et limites explicitement documentés

  • Le jeu phishing est dominé par fake_exchange (19/36) ; les métriques par catégorie ne sont pas statistiquement exploitables.
  • Les catégories phishing sont souvent déduites du domaine et marquées unverified ; seule la vérité terrain binaire phishing/légitime est utilisée.
  • Des pages de login, support, airdrop officiel et wallet-connect légitimes ont été ajoutées pour réduire le confondant « page d’action = phishing ».
  • Les timeouts de certains sites légitimes peuvent provenir d’un filtrage réseau ou géographique, mais cette hypothèse n’est pas déclarée comme un fait.

Protocole du run conservé

Le rapport v1 contient 40 entrées candidates, dont 32 traitées et 8 exclues comme non mesurables (dead: 6, refused: 2). La classification est volontairement stricte : seul verdict === "malicious" compte comme prédiction positive ; suspicious reste une décision de revue manuelle et est donc négative pour le calcul du rappel.

Matrice de confusion

Réalité / prédiction Malicious Non malicious
Phishing TP = 6 FN = 7
Légitime FP = 0 TN = 19

Formules

Précision = TP / (TP + FP)
Rappel = TP / (TP + FN)

F1 = 2 × précision × rappel / (précision + rappel)

Cible : précision ≥ 85 % et rappel ≥ 80 %.

Analyse par chemin d’exécution

Groupe n TP FP FN TN Lecture
Gemini 7 6 0 0 1 100 % précision et rappel sur ce sous-ensemble très réduit.
Aucun modèle 25 0 0 7 18 Le court-circuit déterministe produit tous les faux négatifs.
Cause racine localisée. Les sept faux négatifs ne proviennent pas d’une mauvaise réponse Gemini. Ils appartiennent tous au groupe none : pour un texte trop court ou une page de challenge, assessContentQuality() interdit tout appel au modèle et force suspicious. La règle protège la précision, mais rend le détecteur aveugle à des indices URL ou structurels encore disponibles.

Ce que les chiffres permettent — et ne permettent pas — de conclure

Conclusions valides

  • Le run n’a produit aucun faux positif parmi 19 cas légitimes mesurés.
  • Le rappel global est inférieur de 33,8 points à la cible de 80 %.
  • Le point de blocage est la politique de contenu, pas le sous-ensemble Gemini observé.

Conclusions interdites

  • Ne pas généraliser « Gemini = 100 % » à partir de sept cas.
  • Ne pas présenter la cible IA comme atteinte.
  • Ne pas compter suspicious comme malveillant pour améliorer artificiellement le rappel.
Reproductibilité à renforcer. Le rapport v1 ne consigne pas encore explicitement le commit, le hash de l’index, la date, la commande exacte, le modèle et les versions de prompts. Le prochain run doit enregistrer ces éléments sans modifier ni écraser le rapport v1.

Améliorer le rappel sans tricher

Le seuil de 200 caractères doit sélectionner un mode d’analyse, et non imposer à lui seul le verdict.

Statut. La spécification Recall v2 est documentée mais n’est pas encore implémentée dans l’état audité. Cette page décrit le travail planifié, pas un résultat acquis.

Trois modes fondés sur les preuves disponibles

Mode 1

combined

Texte exploitable : URL, features déterministes, extrait textuel et digest structurel alimentent le même cadre de validation.

Mode 2

url_structural

Texte court mais structure utile : champs de formulaire, scripts externes et motifs Web3 restent analysables.

Mode 3

url_only

Contenu absent, vide ou challenge : analyser l’URL et ses features, sans considérer l’absence comme preuve.

Features URL déterministes prévues

scoreURL = 0,30 × scoreTLD + 0,25 × scoreAgeDomaine + 0,20 × scoreHomoglyphe + 0,15 × scoreSousDomaines + 0,10 × scoreRaccourcisseur
  • Parser standard URL et Public Suffix List pour le domaine enregistrable.
  • Liste fermée de TLD suspects et de raccourcisseurs.
  • Âge RDAP figé dans le cache ; aucune requête réseau pendant l’évaluation.
  • Détection punycode et table documentée de confusions visuelles.
  • Nombre de sous-domaines calculé avant le domaine enregistrable, jamais depuis le path.
  • Valeur neutre 0,5 lorsque l’âge du domaine est indisponible.
  • Une seule feature ne suffit pas automatiquement à déclarer malicious.
  • Aucune URL du jeu final codée en dur dans la logique.

Corriger la sémantique de confiance

Le champ confidence mesure la confiance dans le verdict retourné, et non le risque de phishing. La transformation prévue est donc :

Verdict Risque LLM utilisé Exemple
malicious confidence malicious 0,90 → risque 0,90
legitimate 1 − confidence legitimate 0,98 → risque 0,02
suspicious 0,50 Cas ambigu → risque neutre, revue manuelle

Le score final devient 0,7 × risque LLM + 0,3 × score URL. Une feature forte ne peut toutefois pas convertir silencieusement un verdict légitime ou suspect en transaction : le garde-fou verdict === "malicious" demeure.

Plan de validation v2

Tests à ajouter

  • Sélection des trois modes et métadonnées associées.
  • URL invalide, IP littérale, co.uk, punycode et domaines hébergés.
  • Aucune fuite de label, source ou catégorie attendue dans le prompt.
  • Fallback, retries et validation identiques pour chaque mode.

Comparaison honnête

  • Conserver le cache et le rapport v1 inchangés.
  • Rejouer le même périmètre et documenter tous les paramètres.
  • Séparer « contenu exploitable » et « disponibilité réaliste ».
  • Exiger précision ≥ 85 % et rappel ≥ 80 %, sans relabeling.
